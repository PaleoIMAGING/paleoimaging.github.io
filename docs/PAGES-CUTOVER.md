# GitHub Pages cutover and rollback runbook

The site is published either by the legacy branch builder (`build_type: legacy`, source `main` `/`) or by `.github/workflows/pages.yml` (`build_type: workflow`). The public URLs do not change. `meetings/feed.ics` is generated by the workflow (`tools/build-ics.mjs`, deterministic DTSTAMP); the committed copy stays in `main` until the Worker no longer reads it.

## How publication is gated

- `pull_request` and `workflow_dispatch` without `deploy` only build, validate and compare with production. They hold read-only permissions.
- A push to `main` always builds. It deploys only if the repository variable `PAGES_PUBLISH` is `true`; `workflow_dispatch` with `deploy=true` deploys manually. Both require `github.ref == refs/heads/main`.
- Only the `deploy` job has `pages: write` and `id-token: write`, and it runs in the `github-pages` environment (branch policy: `main` only).
- One publication at a time (`concurrency: pages-production`, no cancellation of a running deploy). While one runs, GitHub keeps only the newest pending run, which contains every earlier commit, so nothing is published out of order.
- Stale protection: the deploy job refuses a revision that is no longer the tip of `main` (the newer pending run publishes instead; the refusal shows as a failed run and is safe).
- With `build_type: legacy` the `deploy` job cannot succeed, which is why `PAGES_PUBLISH` stays unset until the source is switched.

## Cutover (maintainer approval required)

Preconditions: latest `Pages` run on `main` is green with `deploy` skipped and `identical: N, different: 0`; `check:ics` passes on `main`; no pending Pages build.

```bash
R=PaleoIMAGING/paleoimaging.github.io
# 1. Switch the publishing source to GitHub Actions
gh api -X PUT repos/$R/pages -f build_type=workflow
# 2. Enable publication on push to main
gh variable set PAGES_PUBLISH --repo $R --body true
# 3. Publish the current main now (otherwise the next push does it)
gh workflow run pages.yml --repo $R --ref main -f deploy=true
```

Equivalent in the web UI: Settings, Pages, Build and deployment, Source: **GitHub Actions**; Settings, Secrets and variables, Actions, Variables, `PAGES_PUBLISH=true`.

Verify: the run's `build` and `deploy` jobs succeed; `gh api repos/$R/pages -q .build_type` is `workflow`; `https://paleoimaging.github.io/`, `/meetings/` and `/meetings/feed.ics` return 200; `node tools/compare-site.mjs <build dir> https://paleoimaging.github.io` shows no differences (DTSTAMP aside).

## Rollback to legacy publication

```bash
R=PaleoIMAGING/paleoimaging.github.io
gh variable set PAGES_PUBLISH --repo $R --body false
gh api -X PUT repos/$R/pages -f build_type=legacy -f 'source[branch]=main' -f 'source[path]=/'
gh api -X POST repos/$R/pages/builds        # build main now
```

The legacy builder serves the **committed** `meetings/feed.ics`, so it must be current. During the transition it can be stale (a YAML-only submission was merged after the cutover). Before or right after switching back:

```bash
git switch -c fix/regenerate-feed origin/main
cd tools && npm ci && npm run check:ics      # fails when the committed feed is stale
npm run build:ics                            # regenerates meetings/feed.ics (DTSTAMP from Git history)
npm run check:ics && npm run check:calendar
git add ../meetings/feed.ics && git commit -m "Regenerate meetings/feed.ics" && git push -u origin HEAD
```

Open a PR (required checks and one review apply; there is no bypass) and merge it, then confirm `/meetings/feed.ics` contains every record. Never roll the Worker back to a version that reads `feed.ics` unless the file is present in `main`.

## After the cutover

Do not remove `meetings/feed.ics` from `main` until the YAML-only Worker is deployed and verified; removal is a separate approved change that also adds the ignore rule and a CI guard.
